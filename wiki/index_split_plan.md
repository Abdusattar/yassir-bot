## Шаг 1, как он сделан на самом деле (12.11.2026)

**Что выяснилось перед разрезом.** Весь JS приложения — одна замкнутая функция
`(function () { ... })();` на ~14 500 строк, с общими переменными. В первом варианте плана
(ниже) стояло «обычные `<script>` по файлам, функции остаются глобальными» — это было
неверно: глобальных функций в приложении нет. Разнести такой код по отдельно загружаемым
файлам без переписывания нельзя (пришлось бы вынести тысячи имён в глобальную область —
конфликты с `window.name`, `top`, `status` и id элементов, риск не нулевой).

**Что сделано вместо этого.** Разрезаны исходники, а не то, что получает телефон:

- `app_src/index.html` — каркас (разметка, 917 строк), на месте стилей и кода — две метки;
- `app_src/css/` — 17 кусков, `app_src/js/` — 33 куска, порядок по номеру в имени;
- `scripts/build_app.py` склеивает их в `mushaf_data/index.html`.

Собранный файл **байт в байт равен** прежнему (sha256 совпал с версией в git до разреза,
1 291 569 байт). Поэтому для прода не изменилось ничего: тот же один файл, тот же деплой,
кэш, service worker, `/api/muf/version`, стенды и тесты. Пункты «что поправить вместе с
разрезом» из первого варианта (deploy.yml, `?v=`, sw.js) не понадобились — они вернутся,
когда дойдём до раздельной загрузки (шаг 3).

**Страховки.**
- `tests/test_app_build.py` в pre-push хуке: `index.html` равен сборке; каждый кусок JS
  разбирается сам по себе (`node --check`, граница не посреди оператора); в каждом куске
  CSS сходятся скобки.
- `build_app.py --adopt` — обратный путь: правку, сделанную прямо в `index.html` (старая
  ветка, решённый конфликт), раскладывает по кускам. Проверено на настоящей правке
  (3 куска изменились, сборка сошлась) и откате.
- День заморозки не понадобился: незалитых веток с `index.html` на GitHub нет, а локальные
  правки переносятся командой `--adopt`.

**Как теперь работать** — раздел «Код приложения» в `CLAUDE.md`.

**Что это даёт и чего не даёт.** Даёт: двое правят разные файлы — конфликтов почти нет
(останется конфликт в собранном `index.html`, он решается пересборкой); код мусхафа лежит в
семи файлах `js/100…170_mushaf_*`, а не размазан по 19 500 строкам. Не даёт: скорости —
телефон получает тот же файл. Скорость — это шаг 3 и свои шрифты.

**Имена кусков** отражают то, что в них сейчас лежит, а лежит исторически вперемешку
(например, в `css/030_hifz_record_pick.css` есть и общие вещи листа). Переносить код между
кусками — уже не «байт в байт», это отдельные маленькие шаги со снимками до/после.

## Шаг Б: перестановки (уже НЕ «байт в байт»)

Каждый перенос - отдельный коммит со сверкой `scripts/app_snap.py` (14 экранов x 2 темы,
Chromium и WebKit, пиксель в пиксель) и тестами. Переносить функции можно свободно
(объявления функций видны во всём замыкании); строки с `var x = …` и `addEventListener`
- только с проверкой порядка: они выполняются по месту.

**Б1 (12.11.2026): мусхаф подряд.** Куски `230…238` (список сур, закладка, отметка
повторения, свайпы, чтение лёжа) стояли после заучивания (`180…220`) - переименованы в
`172…178`, теперь весь мусхаф идёт `100…178`. Что проверено до переноса:
- код верхнего уровня в этих кусках не читает переменные, которые заводятся в `180…220`
  (обращения к `hifz`, `BAQARA_START_PAGE` - только внутри обработчиков, они срабатывают позже);
- общих целей у слушателей нет, кроме `window resize` - поэтому обработчик поворота и всё,
  что после него выполняется сразу (`mushafOrientationApply()`, первая `loadPage`, отметка
  `open`), вынесено в `239_app_start` и осталось на прежнем месте: порядок запуска тот же.

**Впереди:** листание кнопками лежит в конце `220_hifz_progress` (обработчики `btn-prev`,
`btn-next`); CSS листа размазан по `010`, `030`, `040`, `050`, `160`.

**Б3 (Эрлан, 12.11 вечером, PR #19): CSS листа - свои куски, «байт в байт»** через
`build_app.py --split`: из `010_base_topbar` со строки `#app {` → `012_mushaf_shell_topbar`
(каркас мусхафа, шапка, меню закладки, выбор суры, 165 строк); из `030_hifz_record_pick` со
строки `.view {` → `032_mushaf_sheet` (лист: `.view`, `#page-wrap`, `#ayah-text`,
`.mushaf-line`, 122 строки). Осталось размазанным: таджвид и цвета текста листа в `040`,
подсказка по слову в `050`, чтение лёжа в `160` - их трогать уже не «байт в байт», это к
задаче стилей (токены, атрибут режима).

## Шаги (каждый — отдельный PR, после каждого приложение работает как раньше)

**Шаг 0. Заморозка.** На время шага 1 (один день) в `index.html` никто не пушит: файл
переезжает целиком, любой параллельный коммит — конфликт на весь файл. Договориться о дне.

**Шаг 1. Механический разрез без изменения кода.** Ни одной правки логики — только
перенос кусков в файлы; порядок выполнения тот же.

```
mushaf_data/
  index.html            разметка + <link>/<script> (~2 000 строк)
  css/base.css          токены, общие элементы
  css/mushaf.css        лист, шапка, заучивание, лёжа
  css/today.css  css/trainers.css  css/ustaz.css  css/learn.css  css/feed.css
  js/core.js            вход, apiCall, T(), trail, heartbeat, вкладки
  js/mushaf.js          лист, шрифты V4, подгонка кегля, подсказка, смысл
  js/hifz.js            40+40, запись, плеер
  js/today.js  js/trainers.js  js/ustaz.js  js/learn.js  js/feed.js
  i18n/ru.json  ky.json  uz.json  zh.json     грузится только выбранный язык
```

Обычные `<script>` в прежнем порядке, без модулей и без сборки: все функции остаются
глобальными, как сейчас. Это скучно, зато риск почти нулевой и откат — один коммит.

Что нужно поправить вместе с разрезом:
- `deploy.yml` копирует на сервер перечисленные файлы — добавить `css/`, `js/`, `i18n/`;
- nginx: `no-cache` сейчас только на `index.html` — новые файлы подключать с версией в
  адресе (`js/mushaf.js?v=<хэш коммита>`, подставляет деплой), иначе вернётся старый кэш
  (ловушка 29.08, `wiki/mushaf_yassirapp.md`);
- `sw.js`: новые файлы в оболочку, поднять `VERSION`;
- `/api/muf/version` считается по времени изменения `index.html` — считать по всем файлам;
- стенды (`scripts/shoot_onboarding.py: dev_index`) подменяют строки в `index.html` — перевести
  на новые файлы;
- словари: `T()` сейчас синхронный. Русский оставить встроенным (он же запасной), остальные
  языки подгружать до первого экрана.

Проверка шага: 842 теста; снимки 390×844 ключевых экранов до и после — попиксельно равны
(мусхаф обе раскладки, заучивание, лёжа, «Сегодня», тренажёр, кабинет устаза), обе темы,
Chromium и WebKit.

**Шаг 2. Проверка типов.** `// @ts-check` + `tsc --noEmit` в CI по файлам `js/` (без
сборки). Ловит обращения к несуществующему и опечатки до прода.

**Шаг 3. Модули и Vite + TypeScript** (как в документе 08.11) — отдельным решением, когда
шаг 1 отстоится. Экран за экраном, начиная с мусхафа.

## Мусхаф: что привести в порядок внутри (после шага 1)

1. **Подгонка кегля** (таблица ширин 604×2, сверка через 0,5 и 1,5 с, поправка на телефон,
   предел по высоте) — логику не менять: каждый слой появился после живого бага на айфонах.
   Собрать в один блок с одним входом и покрыть стендом. Решение Абдусаттара 12.11: «потом
   подумаем».
2. **Слова в данных листа записаны дважды** — в `ayahs` и в `lines`. Предложение: единственный
   источник — `lines`; `ayahs` хранит номера и смысл, слова берёт ссылкой (строка, позиция).
   Делать при следующей пересборке страниц, не раньше: это 604×2 файла и языковые версии.
   Выигрыш — один источник правды (сейчас `scripts/patch_mushaf_ru.py` правит оба места).
3. **Шрифты** — один вход `loadV4Face`, свой сервер первым.

## Стили — предложение Эрлану

Задача отдельная от разреза; вести её удобнее тому, кто делает макеты.

- Токены: цвета, отступы, кегли — только через переменные `:root`; разовые значения в
  правилах собрать в токены (сейчас их добавляли по мере фич).
- Режимы экрана: вместо россыпи `body.tabs-mushaf #x { display: none }` — один атрибут
  состояния (`data-mode="page|hifz|review|land"`) на корне мусхафа и правила от него.
- 17 `!important` — разобрать по одному: каждый означает, что два правила спорят.
- Мёртвые правила: после шага 1 прогнать покрытие CSS по стендам (Chromium coverage) и
  убрать то, что не срабатывает ни на одном экране.
- Обе раскладки (Мадина, Дар аль-Маариф), обе темы, RTL — проверять снимком.
