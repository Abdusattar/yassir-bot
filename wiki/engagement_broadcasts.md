# Рассылки вовлечения — анкета студента и приглашение друзей

Две независимые фичи из бэклога 12.08.2026 («анкета "откуда и сколько лет"
через месяц», «рассылка про приглашение друзей»). Обе — личные сообщения
(требуют `dm_ok=1`), обе не связаны с prep-группой напрямую.

## Анкета "откуда и сколько лет" (`core/prep.py`-соседний слой — фактически `core/scheduler.py` + `core/db.py`)

Редизайн 17.08.2026 поверх версии от 13.08 (триггер, батчинг и
admin-исключение сменились — см. ниже). Студенту в личку задаётся 2
вопроса по очереди: сначала место (откуда сдаёт задания СЕЙЧАС, не
происхождение), после ответа — возраст. Ответы хранятся только в БД,
никому не пересылаются.

- Схема: `users.survey_stage` (`NULL` → `asked_location`/`location_retry`
  → `asked_age`/`asked_age_retry` → `done`), `users.survey_location`,
  `users.survey_age`, `users.survey_birth_year` (год рождения, посчитан
  из ответа на возраст — не сам возраст, чтобы не устаревал),
  `users.survey_stage_at` (момент последнего перехода стадии).
- **Триггер:** 2 дня после перевода в постоянную группу
  (`user_groups.joined_date`), не 30 дней после регистрации, как было
  13.08 — у старых студентов между регистрацией и реальным началом мог
  быть большой разрыв.
- `get_users_due_for_survey()` (`core/db.py`) — активные студенты в
  pro/relaxed, `dm_ok=1`, `joined_date` ≥2 дня назад, `survey_stage IS
  NULL`. Без `LIMIT` — батч по 5/день из осторожности убран прямым
  решением пользователя (разовый запуск всем подходящим сразу 17.08,
  дальше органическое пополнение).
- **Устазов/админов, которые ГДЕ-ТО ТОЖЕ студенты, больше не исключает**
  (было исключение 13.08 — снято 17.08, общая политика, решение
  пользователя). Раньше исключение было нужно, потому что перехват ответа
  анкеты в `handlers.py` не был ограничен по времени: обычная команда
  устаза могла перехватиться как ответ на `survey_location` и застрять
  навсегда. Теперь это больше не проблема — см. окно ниже. Чистых админов
  без активной роли `student` нигде (например Умар устаз) фильтр не
  касался и не касается — они не проходят JOIN по `role='student'`.
- **Окно ответа — 24 часа** (`survey_answer_in_window`, `core/db.py`) с
  момента вопроса. Ответ, пришедший позже, НЕ перехватывается как ответ
  на анкету (обрабатывается как обычное сообщение) — иначе случайное
  сообщение через дни после вопроса могло ошибочно записаться в анкету.
  Вопрос остаётся висеть, откроется заново еженедельным повтором.
- **Переспрос (один раз, не бесконечно):** если ответ на возраст не
  содержит числа — `asked_age_retry`; если ответ на локацию похож на
  голое приветствие («Ваалейкум ассалам» и т.п., рефлекс на текст
  вопроса — реально ловилось на живых ответах, 3 из первых 10) —
  `location_retry`. Второй ответ принимается как есть в любом случае, не
  мучает бесконечно. Приветствие убрано из текста первого вопроса
  (`profile_survey_q_location`) как основная профилактика.
- `profile_survey_nudge()` (`core/scheduler.py`, слот 07:00 ежедневно,
  вместе с `profile_survey_intro`) — застрявшим на любой из
  промежуточных стадий ≥7 дней без ответа повторяет ТОТ ЖЕ вопрос (не с
  начала). Заодно частично лечит случаи устаревшего `dm_ok=1` (первая
  отправка реально не дошла) — следующая попытка через неделю может
  пройти.
- Перехват ответа — в `core/handlers.py`, сразу после хука `was_dm_ok`,
  ДО всех остальных веток личных сообщений. Команды (`/help` и т.п.) не
  считаются ответом.
- `profile_survey_intro()` (`core/scheduler.py`, слот 07:00 ежедневно) —
  **выключена по умолчанию**: `bot_settings["profile_survey_enabled"] !=
  "1"` → функция сразу выходит. Включение — `set_setting(...)` на
  сервере, без редеплоя (`bot_settings` не общий между ботами — включать
  на каждом отдельно).
- **Статус на 17.08.2026:** включена на мужском боте (74 + 11 дозже
  устазов-студентов = 85 отправлено разом, не батчами). Женский
  выключен — пользователь прямо попросил пока не трогать.

## Рассылка "позови друга" (`core/scheduler.py::invite_friend_broadcast`)

Раз в 2 недели (нечётные ISO-недели, четверг 10:00 —
`now.isocalendar()[1] % 2 == 1`) в личку всем активным студентам кроме
подготовительной — короткое сообщение с призывом позвать друга к Корану +
ссылка на подготовительную группу (`get_prep_group()["invite_link"]`,
единая точка входа новых студентов). Без трекинга и бонусов.

- **Дедуп по `phone` обязателен.** Студент может состоять в 2 группах
  одновременно (обычная + Тадаббур — «общая группа где все студенты
  находятся»), цикл идёт по `get_all_groups()` × `get_students(group_id)` —
  без дедупа отправка дублируется. На проде разница — 181 «сырых» строк
  против 104 реальных людей.
- 6 вариантов текста по кругу (`invite_friend_1`..`_6` в `i18n.py`),
  индекс — `bot_settings["invite_friend_last_index"]` (свой на каждом
  боте — `bot_settings` не общий между мужским/женским, отдельные файлы
  БД).
- Текстовый регистр — принципиально НЕ маркетинговый. Первый черновик
  постоянно упоминал «наш проект» («пригодился бы наш проект», «проект
  растёт от тех, кто зовёт») — пользователь отверг сразу, финал написан
  в регистре «друг + Коран», без слова «проект» в теле почти везде (тот
  же принцип, что `feedback_no_accusatory_tone` — проект про Коран, не
  про метрики). Все 6 вариантов содержат условие «друг уже умеет читать
  Коран» — проект не учит чтению с нуля.
- Сознательно без цитат хадисов — риск неточной цитаты в религиозном
  тексте выше пользы; если понадобится конкретный хадис — брать из
  `sources/hadiths.db` (используется в `sampler.py` для `tadabbur_nasiha`
  и т.п.), не сочинять заново.

## Общий урок для будущих массовых рассылок студентам

Перед первым включением любой новой рассылки — считать реальный охват на
прод-БД (сколько получат первую волну, есть ли дубли из-за multi-group
членства, есть ли пересечение с устазами/админами), а не полагаться на
логику "на пустой тестовой БД работает". Оба фикса в этом разделе найдены
именно так, до деплоя, не после.
