# Яссир — правила работы для Claude (общие для всей команды)

Проект — платформа заучивания Корана: Telegram-боты + веб-приложение YassirApp (yassirilm.com).
Над проектом работают несколько человек, у каждого свой Claude. Этот файл — общая память:
всё, что должен знать любой Claude до первой правки.

## Перед любой работой

1. **Сначала понимание — потом код.** Нетривиальная задача: кратко изложи, как понял →
   уточни → предложи лучший подход, если видишь → получи «да» → только тогда пиши.
2. **Сначала wiki.** `grep` по `wiki/*.md` по теме задачи ДО начала работы. Там решения,
   причины и грабли, которых нет в коде. `context/summary.md` — где остановились.
3. **Сначала git-история.** На коде с повторными правками — `git log -p` по файлу до фикса.
4. **Параллельная работа.** В репо работают несколько людей и сессий. Чужие незакоммиченные
   правки не трогать, `git add` только своих файлов (не `git add -A`). Перед работой `git pull`.

## Деплой — золотое правило

- **Push в `master` = выкатка на прод.** GitHub Actions (`.github/workflows/deploy.yml`) делает
  `git pull` на сервере, перезапускает ОБА бота и проверяет порты 8081/8082. Руками не рестартовать.
- Pre-push хук гоняет синтаксис + все тесты (~1 минута, замер 12.11: 842 теста за 64 с). Молчащий push — это хук, а не сеть.
  Включить хук: `git config core.hooksPath .githooks`.
- После пуша проверить, что Actions зелёный И что прод реально на новом коммите
  (бывало: зелёный, а сервер на старом — см. `wiki/infrastructure.md`).
- Проверять фиксы через публичный URL (yassirilm.com), а не путь на сервере.
- Мелочь — сразу на прод, долгие прогоны — фоном.

## Два бота — две половины

- Мужской (`BOT_PROFILE=male`, `quran_male.db`) и женский (`female`, `quran_female.db`).
  **Код один, базы разные.** Ручные данные лить в обе базы.
- Половины не смешиваются: брат не попадает к сёстрам и наоборот.
- Общий бот-вход наружу — @YassirAppBot (токен только в мужском `.env`).
- Подробно: `wiki/infrastructure.md`, `wiki/one_bot.md`.

## Данные и база

- **Не править прод-БД руками.** Находим причину в коде и чиним код.
- `sqlite3.Row` не поддерживает `.get()` — всегда `row["key"]`.
- Устаз = `user_groups.role='admin'`, НЕ таблица `group_admins` (заброшена). Две похожие
  таблицы — сначала проверить, какую реально читает код.
- Устаз реален только в своей группе; все устазы, кроме Умар устаза, сами студенты в другой группе.
- `users.phone` — это Telegram ID, а не номер телефона.
- `score_events.created_at` — UTC, `date` — Asia/Bishkek. Расхождение — артефакт, не правило.
- Telegram шлёт два события на один вход в группу — обработчики должны быть идемпотентными.
- Bot API не даёт список участников группы.
- Массовые действия (kick/ban/рассылки) — исключать админов (`SUPER_ADMIN_IDS`, `is_any_group_admin`).
  Перед классификацией людей смотреть полную историю, не только `active=1`.
- Переиспользуемые скрипты держать в `scripts/`, а не писать одноразовые.

## Коран и религиозный контент — жёстко

- **Никогда не выдумывать переводы Корана и хадисов.** Только реальные источники
  (ru: Кулиев через api.quran.com; ky/uz: quranenc.com). Цитаты — только из базы.
- Тексты банка насых — в выдачу только `approved=1`, отметку ставит человек после сверки.
- Арабское сравнивать по буквам (без харакатов) — порядок шадды/фатхи бывает разный.
- Коррекции Умар устаза (хафиз, 25 лет с Кораном, Мединский университет) — ground truth.
- Результат — только от Аллаха: в текстах не приписывать результат инструментам.

## Тексты бота и UI

- Бот говорит от первого лица («я»); объявления об изменениях — от «Команды Яссир» («мы»):
  что изменилось → зачем → было/стало → что делать.
- Тон без обвинительного оттенка: проект про Коран, не про наказания.
- Писать «Умар устаз» (имя первым).
- **Тексты студентам показывать человеку до отправки** (полный текст + получатели → «да» → отправка).
- ИИ студентам не отвечает (флаг `AI_ANSWER_QUESTIONS` выключен).
- Новые фичи — сначала только на русском; ky/uz одним проходом потом (`T()` откатывается на ru).
- Любая правка UI — снимок 390×844 глазами до пуша. RTL-вещи (арабский, «7-бет», «»)
  проверять только скриншотом. iOS Safari от iPhone 11 (iOS 16.2+); Playwright WebKit ≠ iOS.
- Мусхаф имеет две раскладки (Мадина и Дар аль-Маариф) — новые фичи обязаны учитывать обе.

## Логи и итоги сессии

- `context/summary.md` — текущее состояние проекта; обновлять в конце сессии.
- `logs/terminal/YYYY-MM-DD.md` — краткий лог решений за день. У каждого свой файл:
  Абдусаттар — `YYYY-MM-DD.md`, Эрлан — `YYYY-MM-DD_erlan.md`.
- **Логи видны обоим через GitHub (12.11.2026).** Лог — не личные заметки, а переписка
  команды: что обсуждали, что решили и почему, что отложили.
  1. В начале сессии после `git pull` посмотреть, что нового у напарника с прошлого раза:
     изменившиеся файлы в `logs/terminal/` и `wiki/` (`git log --stat` по этим папкам) —
     и прочитать их до первой правки.
  2. Лог коммитить и пушить в конце сессии и вместе с каждым заметным пушем кода —
     не копить локально.
  3. Писать так, чтобы понял человек без контекста сессии: решение → причина → коммит.
     Обсуждения и отвергнутые варианты тоже — одной-двумя строками.
  4. Предложения, которые ждут согласования, — документом в `wiki/` со статусом в шапке.
  5. **Поиск по блокам.** `wiki/README.md` — карта: блок Яссира → файлы вики. Каждый раздел
     лога начинается с метки блока из этой карты: `## [Мусхаф] …`, `## [Тренажёры] …` —
     тогда история блока находится одним `grep -rn "\[Мусхаф\]" logs/terminal/`.
  6. Вики ведут оба одинаково: долгосрочное знание (решение, причина, грабли) — в `wiki/`
     по теме с датой, в тот же пуш, что и код. Лог — «что было сегодня», вики — «как устроено».
- Долгосрочные знания — в `wiki/` (по теме, с датой и «почему»).
