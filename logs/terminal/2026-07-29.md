## Найденный баг

- Реальный случай: студента перевели в Тадаббур за неактивность (`reason ==
  "inactive"`), но личное сообщение (DM) со ссылкой на подготовительную
  группу студенту **не отправлялось вообще** - только сообщение в группу,
  которое кикнутый студент уже не видит.

## Фикс (`core/transfers.py`, `_transfer_to_tadabbur`)

- Добавлена отправка DM студенту **до** объявления в группе, отдельно для
  `reason == "inactive"`: текст `transfer_to_tadabbur_dm` (с деталями периода
  и названием группы) либо `return_needs_prep_dm`, если детали недоступны.
- Если DM не доставлен (`dm_ok=False`, студент не писал боту в личку) -
  админам летит доп. уведомление `transfer_dm_failed_notify_admin`, чтобы
  объяснить условия возврата вручную.
- Сообщение в группу упрощено - убраны детали условий возврата (кикнутый их
  всё равно не видит, оставлено только для тех, кто остался в чате).
- `handle_member_left`: объявление `student_left_group` теперь не шлётся,
  если студент вышел/выведен именно из группы `tadabbur` (там это
  сообщение неуместно/избыточно после перевода).

## Правило возврата из prep для кикнутых из Про-группы (продолжение сессии)

Обсуждали маршрут возврата студента, кикнутого из Про за пропуски, после
того как он проходит подготовительную (prep) заново. Правило менялось
**трижды** за одно обсуждение — фиксирую финальную версию и отброшенные
варианты, чтобы следующая сессия не приняла старое сообщение в истории за
актуальное решение:

1. ~~Relaxed всегда, апгрейд в Про только через существующий механизм
   27/30 дней (`_check_upgrade`)~~ — отброшено.
2. ~~Обычный вопрос про джуз без исключений (да → N-1, нет → relaxed)~~ —
   отброшено.
3. ~~Кикнутый из Про возвращается в ту же группу без вопроса про джуз~~ —
   отброшено (это был промежуточный вариант, коммит на него не делался).
4. **Финал**: вопрос "знаешь ли больше джуза" задаётся как обычно всем.
   - Знает больше джуза → N-1 (топовая группа), как для всех остальных.
   - НЕ знает больше джуза И был кикнут именно из Про-группы
     (`pending_prep_return.from_group_id` указывает на группу с
     `group_type='pro'`) → возвращается в ТУ ЖЕ Про-группу, а не в
     обычную relaxed.
   - НЕ знает больше джуза И не было кика из Про (обычный новый студент
     или кикнут из relaxed) → как раньше, наименее заполненная relaxed.

### Реализация (`core/prep.py`, `core/db.py`, `core/i18n.py`)

- `get_pending_prep_return_from_group_id(phone)` (`core/db.py`) — новый
  геттер поверх `pending_prep_return.from_group_id`.
- `_pro_return_origin(phone)` (`core/prep.py`) — возвращает исходную
  Про-группу (с проверкой `active=1` и `group_type='pro'`) или `None`.
- `handle_juz_answer`: при `knows_juz=False` сначала проверяет
  `_pro_return_origin`, добавлен `target_type="pro_origin"`.
- `check_prep_students` / `remind_ustaz_about_graduate`: место повторной
  отправки ссылки (студент ответил, но ещё не вступил) теперь смотрит на
  `subcategory` ответа и шлёт `prep_return_to_origin` вместо
  `prep_juz_result`, если это `pro_origin`.
- Новый i18n-ключ `prep_return_to_origin` (ru/ky).
- Язык origin-группы не проверялся отдельно: `get_prep_group()` не
  фильтрует по языку (единая prep-группа на все языки), поэтому возврат в
  группу-источник по факту безопаснее по языку, чем общий путь через
  relaxed — отдельный guard не нужен.

### Не проверено

- Живой прогон (нет тестов на `core/prep.py` вообще, только `pytest`
  25/25 на остальном коде + `py_compile`).
- Что происходит, если студент дважды подряд проваливает prep, будучи уже
  привязанным к одной и той же Про-группе через `pending_prep_return` —
  маркер снимается только при реальном официальном выпуске
  (`announce_prep_graduate_arrival`), так что при повторной попытке он
  снова попадёт в ту же Про-группу. Признано корректным поведением
  (маркер = "должен туда вернуться"), не багом.
