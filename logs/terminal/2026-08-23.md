# 23.08.2026 — сессия

## Устаз-наблюдатель со стороны (`/ustaz`)

Запрос пользователя: кандидат в устазы сам вызывает команду, сообщение
уходит суперустазам, после подтверждения может заходить в любую группу
как наблюдатель — бот его полностью игнорирует. Уточнение по ходу
обсуждения: это ОТДЕЛЬНАЯ, более слабая роль — полноценным устазом
конкретной группы (права `/bonus`, отметка голосовой, «у») человек
становится только через существующий `/admin` (реплай суперадмина внутри
группы), эта заявка его не заменяет.

Реализация: `/ustaz` (личка, доступна любому, даже незнакомому боту
человеку) → уведомление всем `SUPER_ADMIN_IDS` с именем/id →
`/approve_observer <id>` ставит `users.is_observer=1` (глобальный флаг),
`/revoke_observer <id>` снимает. Проверка `is_observer` добавлена в оба
Telegram-пути входа в группу — не только когда человек ПИШЕТ сообщение
(`handlers.py`), но и когда он ВСТУПАЕТ (`chat_member`/`new_chat_members`
в `bot.py`) — оба пути независимо регистрируют/приветствуют новичка,
без защиты второй путь пропустил бы наблюдателя мимо первой проверки.
Advisor поймал это до деплоя, плюс отсутствие команды отзыва — оба
блокера закрыты в том же заходе.

Попутно, по прямой просьбе — удалена команда `/bonus` (ручное начисление
баллов устазом): хендлер, `/help` на всех 5 языках, `knowledge/
project_info.md` (иначе Ясир продолжал бы рассказывать про
несуществующую команду в ответах).

## Баг с бонусом за стрик — Арген (G-2b)

Пользователь показал реальный еженедельный отчёт: Арген — 7 дней подряд
полной сдачи, но без бонуса +5, хотя другие с меньшим числом дней бонус
получили. Разбор на сервере (только чтение): у Аргена ещё в июне-июле
была долгая беспрерывная серия, за которую честно получены бонусы
`week_1`…`week_5`. После пропуска 14.08 серия обнулилась, новая честная
7-дневная серия набралась к 21.08 — но `streak_bonuses()` проверяла
«получал ли этот студент КОГДА-ЛИБО бонус с меткой week_1» без привязки
к дате, метка уже была использована в июне → бонус молча пропускался.
Баг системный, не только про Аргена — любой, кто хоть раз прерывал
длинную серию и потом набирал новую, страдал бы так же.

## Решение пользователя: бонус — календарная неделя, не скользящая серия

«У нас в неделю только один бонус — если 7 раз не пропуская все дни
сдавал, календарные, все задания». Это не патч дедупа, а другая модель:
+5 начисляется один раз за ЗАВЕРШЁННУЮ календарную неделю (пн-вс) тому,
кто сдал все задания все 7 дней без пропуска, дедуп по неделе
(`cal_<понедельник>` вместо `week_N`) — коллизия с прошлой историей
невозможна в принципе. `streak_bonuses()` (07:00 ежедневно) больше не
начисляет баллы, только мгновенная AI-похвала на живых рубежах серии
(7/14/30 дней подряд) — эту часть пользователь явно попросил оставить,
она не про баллы.

## Объединение двух недельных отчётов + календарная неделя

Отдельный вопрос пользователя: «зачем нам два отчёта то недельного?»
(рейтинг+похвала лидеру по воскресеньям 19:00, скользящее окно; список
частичных сдач по понедельникам 07:00, календарная неделя). Прямой
запрос: «надо объединить и сделать один, и он должен быть не
скользящим, а понятным, то есть календарным недельным». Одна функция,
запуск пн 07:00 (вт — подстраховка, как раньше у частичного отчёта),
календарная неделя пн-вс для обеих частей. Также попросил короче
формулировать текст бонуса — не длинное объяснение в скобках у каждого
имени, а общий заголовок «Получили +5 за постоянство» + список.

Advisor поймал 2 реальных бага в готовой реализации до деплоя:
- Забытый старый слот вс 19:00 остался в расписании параллельно с новым
  пн 07:00 — дал бы двойной отчёт, первый про позапрошлую неделю.
- `AND (? IS NULL OR u.phone != ?)` в SQL-исключении устаза — для
  студента с `phone IS NULL` сравнение `NULL != X` даёт NULL (не true),
  студенты без Telegram ID молча выпадали из ВСЕГО рейтинга. Поправлено
  на явную проверку `u.phone IS NULL OR u.phone != ?`.

## Развилка: суперадмин в G-2b — реальный студент, не только формально

Черновая версия фикса (по мотивам жалобы «бот меня комментирует в
тадаббуре») заодно исключала суперадмина (пользователя) из рейтинга/
студенческого потока ВЕЗДЕ — обоснование было из `wiki/weekly_reports.md`
(«он сам активный "студент" в G-2b», причина исключения из ДРУГОЙ фичи).
Пользователь уточнил прямо: «я обыкновенный студент помимо всего именно
только в группе G2b» и «я студент в том числе» (про месячный рейтинг) —
то есть в G-2b участие настоящее, не случайная запись, исключать оттуда
неверно. Широкий фикс (`is_group_admin(phone, group_id): return`
безусловно) откачен обратно на исходную двухстрочную проверку. Вместо
него — точечная деактивация именно тадаббурской студенческой записи
(user_id=7, group_id=7) через штатную `deactivate_student` (не руками в
БД), G-2b не тронут.

## Системный баг: студенты без Telegram ID никогда не переводились за пропуски

Вопрос пользователя: «студент АбдулЛах в н-2а, давно не сдает, но бот
его не кикает, почему?». Разбор: Абдуллах (id 28) добавлен `/add Имя`
без номера — устаз может заранее внести имя из списка, ID привязывается
автоматически при первом сообщении в чате; Абдуллах ни разу не написал.
`_check_group_for_transfers` (`core/transfers.py`) пропускал таких на
самой первой строке (`if not student["phone"]: continue`) — не просто
не банил физически (это ожидаемо, нечем), а вообще не деактивировал и
не переводил в тадаббур ВНУТРИ БАЗЫ, хотя ежедневно назывался по имени в
`morning_reminder` (без фильтра по телефону). Проверка показала второй
такой же случай в той же группе — Азис (id 29), тоже добавлен 21.06 без
номера, 63 дня без единой сдачи. Всего по всей базе — ровно 2 таких
студента, оба в N-2a.

Пользователь уточнил вопрос про физический кик: «меня интересует именно
физическое посылание» — проверено эмпирически (не по памяти): Telegram
Bot API не даёт список участников группы даже когда бот сам админ,
только `getChatAdministrators` (список админов) и `getChatMemberCount`
(число); пассивный кэш имён бота (`cache_member_name`, заполняется при
ЛЮБОМ сообщении в чате) для Абдуллаха/Азиса тоже пуст — оба ни разу не
писали. Значит бот физически не может их кикнуть ни при каких правах,
только внутри-базовый перевод. Фикс: ранний `continue` убран, общий
порог пропусков применяется и к безID-студентам — деактивация+перевод
работают как обычно, физический бан и личное DM явно пропускаются
(`if student["phone"]:` вместо падения в общий `except`).

Азис обработан вручную в этой же сессии (не дожидаясь автопроверки
21:00): деактивирован в N-2a, поставлен маркер `mark_pending_prep_return`
(с оговоркой — без ID маркер не свяжется с его будущим реальным
аккаунтом напрямую, но общий гейт «незнакомый Telegram ID → сначала
подготовительная» всё равно даёт тот же результат), сообщение в группу
отправлено. Физически из Telegram-группы убрал сам пользователь.
**Абдуллах — открытая задача**, тот же случай, пользователь отложил
решение на потом.
