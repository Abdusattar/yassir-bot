## Обрезание строк мусхафа на iPhone 15

Жалоба: на iPhone 15 каждая строка страницы чтения срезается слева (в RTL —
конец строки), на Pixel 7 та же страница влезает целиком (`materials/обрез.jpeg`).

Разбор: размер шрифта в `clampFontToFit()` считается ОДНИМ пересчётом по
пропорции (замер при базе 40px → линейное масштабирование). Пропорция верна,
только если движок отрисует ровно с той же относительной шириной. WebKit и
Blink шейпят один шрифт по-разному; плюс замер может попасть в кадр, когда
контейнер ещё не финальной ширины (WebView Telegram на iOS доводит вьюпорт
после старта). Лишнее молча срезает `overflow-x: hidden` у `#page-wrap`.

**Решение (согласовано):** ветку «если Safari/iOS» НЕ делаем — она угадывает
движок. Вместо этого самопроверка: после применения размера спрашиваем сам
браузер (`scrollWidth` строки > её `clientWidth`), и если не влезло — ужимаем
и проверяем снова, до 20 проходов. Шаг не вслепую: берём ровно недостающую
долю, но не больше 1% за проход. Отдельно оговорено пользователем: у тех, у
кого и так всё нормально, не должно пропадать даже 1% — цикл выходит на первой
же проверке, не отняв ничего.

Проверено симуляцией: Pixel (замер верен) — 0 проходов; промах движка на 9% —
7 проходов по 1%; грубый промах 25% — упирается в предел 20 проходов.

## Тренажёр: жалоба Сатара из 2б (ждёт решения)

1. **Ложное «Слова на закладке закончились. Сдвинь страницу».** Каждый 3-й
   вопрос (`STARRED_QUESTION_QUOTA = 3`) обязан брать цель из «Моих слов». Если
   подходящей цели там нет (все выучены / отфильтрованы как частый перевод),
   `generate_question` возвращает `None`, и оба транспорта трактуют это как
   «пул исчерпан». Отката на обычный пул нет — это баг. **СДЕЛАНО:**
   `generate_question` при пустой (после фильтров) звёздной выборке берёт цель
   из обычного пула; None теперь означает ровно одно — выучен сам основной пул.
   Три теста в `tests/test_mufradat_question.py`, первый падает без фикса.

2. **«Закреплено 21» не двигается несколько дней.** Следствие
   `COVERAGE_WAVE_SHARE = 0.8` (30.08): 80% вопросов из волны наименее
   показанных слов. При 1000+ ни разу не показанных слов волна всегда состоит
   из новых, а «закреплено» требует 3 верных подряд (`MASTERY_STREAK = 3`) —
   слово со стриком 1 возвращается только через оставшиеся 20%. Охват растёт,
   закрепление стоит. Предложено: третья корзина — слова со стриком 1–2 берут
   часть доли у волны новых. **СДЕЛАНО, пропорции согласованы:** 50% волна
   новых / 30% закрепление (стрик 1..MASTERY_STREAK-1) / 20% общий пул. Пустая
   корзина закрепления отдаёт долю волне. Симуляция (1000 слов, 40 ответов в
   день, точность 90%, 14 дней): было — закреплено 0, охвачено 518; стало —
   закреплено 36, охвачено 381. То есть старые пропорции действительно
   ЗАМОРАЖИВАЛИ закрепление полностью.

## Сдача из приложения в подготовительной группе

Жалоба: в режиме заучивания кнопка «Сдать» отвечает «Ты пока не в учебной
группе» — prep-студент не может отправить выученное прямо из приложения.

Причина системная: `get_learning_group()` по определению отдаёт только
pro/relaxed, prep исключён. На этой функции висят ВСЕ ТРИ способа сдать из
приложения — `m` (запись 40+40), `r` (кнопка «повторение»), `t` (зачёт «Слова»
в тренажёре). То есть prep-студент не мог засчитать из приложения ничего, хотя
у prep-группы те же задания (проверено на проде: «Yassir подготовительная»,
tasks='m,r,t', chat_id есть, 15 активных студентов).

**Решение:** флаг `include_prep=True` в трёх местах приложения, а НЕ снятие
исключения для всех вызовов. Причина: на той же функции держится проверка
регистрации в handlers.py — считай она prep учебной группой, выпускник
подготовительной при входе в постоянную группу получал бы «ты уже студент
группы «Yassir подготовительная»», то есть ломался бы сам переход, ради
которого подготовительная и существует. Рейтинг флаг не трогает — участие
prep в групповом рейтинге остаётся отдельным решением.

Постоянная группа в выборке идёт первой: в момент перехода студент недолго
активен и там, и в prep, сдача должна уйти в новую группу.

## Кабинет устаза — первый заход по макету

Жалоба: в кабинете висят 126 (уже 141) заданий, при этом пользователь не
проверяющий устаз ни в одной группе.

Разбор на проде: он числится `role='admin'` в группе 14 «Yassir
подготовительная» — все 141 оттуда. У Умар устаза (7666229019) в G 2b / N-1 /
N-2a — 289 непроверенных. Причина завала: `reviewed_at` ставится ТОЛЬКО на
реплай устаза в группе; где реплаями не отвечают, копится с самого старта.
**Пользователь уточнил: устаз prep — тоже Умар устаз.**

Макет (артефакт 33dd29fb, «Заучивание 40+40») требования уже покрывает:
зоны «Ждут»/«Студенты»/«Проверено», переключение группы тапом по названию,
у каждой сдачи место + дата/время + «ждёт 2 дня» краснеет. Чего в макете нет —
окна по дате; это добавка этой сессии.

**Решения (согласованы):** окно 3 дня, хвост свёрнут строкой «ещё N старше»;
порядок работ — сначала окно + группы, «Студенты» вторым заходом, «Проверено»
позже; место сдачи писать в БД (миграция, только для новых сдач).

**Сделано:** миграция `hifz_page/hifz_line/hifz_stage`; окно
`USTAZ_WINDOW_DAYS = 3`; `count_pending_voice_reviews`; счётчик на двери
считается по окну; `/api/muf/ustaz/waiting` отдаёт группы с числами, окно,
размер хвоста и серверную дату; `?older=1` раскрывает хвост отдельным
запросом. Фронт: список групп с фильтром тапом, строка = имя + место + когда +
«ждёт», свёрнутый хвост. «Сколько ждёт» считает сервер (часовой пояс телефона
устаза не при чём). 5 тестов, вся сюита 119.

**Открытый вопрос:** Умар устаз не числится админом в prep — чтобы prep-сдачи
попали в его кабинет, нужен реплай на его сообщение в prep-группе + `/admin`.

## Кабинет устаза — второй заход: супер-админ и красные счётчики

Решения пользователя (04.09.2026, по ходу сессии):
- супер-админ видит ВСЕ активные группы, устаз группы — только свои;
- над каждой группой красным число непроверенных, «чтобы устазы сразу видели»;
  рядом приглушённо «ещё N» — хвост старше окна, чтобы «10 · ещё 131» не
  читалось как 141 сегодняшних;
- счётчик на двери: у устаза — по своим группам, у супер-админа — ОБЩИЙ.
  Причина: Умар устаз как супер-админ реально проверяет чужие группы, когда
  устаз группы не успел, значит общий долг для него — свой долг;
- дверь «Устаз» видна супер-админу даже без единой роли устаза — иначе,
  сняв с себя роль в подготовительной, он терял кабинет целиком.

**Права на приём отдельно выдавать не пришлось:** `is_group_admin`
(core/handlers.py:218) уже возвращает True супер-админу в ЛЮБОЙ группе —
его реплай или реакция закрывают сдачу где угодно. Проверено по коду.

Как снять с себя роль устаза: в группе реплай на СВОЁ сообщение + `/unadmin`
(бот берёт автора сообщения, на которое отвечают — bot.py:336). Назначить
Умара: реплай на его сообщение + `/admin`. Пользователь решил пока не снимать.

Шесть тестов эндпоинта через настоящий aiohttp-стек (важная деталь:
Application строится ВНУТРИ цикла событий, иначе «initialized with different
loop»). Вся сюита — 125.
